# InkAgent launch video

Remotion, 1920×1080, 30 fps, 2010 frames (67 s). The only asset is the project's
own product photograph, `firmware/docs/images/cover.jpg`, copied to `public/`.

```
npm run dev      # Remotion Studio
npm run audio    # rebuild public/score.wav and public/vo.wav
npm run render   # out/inkagent-launch.mp4, mastered
```

`npm run audio` is needed once after a clone: the two tracks are generated, so
`audio/` is in the repo and the WAVs are not.

`LaunchVideo` is the whole cut. Each beat is also its own composition
(`scene-open`, `scene-native`, `scene-detects`, `scene-reading`, `scene-memory`,
`scene-apps`, `scene-end`) so one can be re-timed or re-rendered alone.

## How the device shots are made

`components/PhotoHero.tsx` composites a live screen into the photograph. The
panel's four corners were measured in the photo; `components/homography.ts`
solves the projective transform that maps a screen authored in device pixels
onto them, and a multiply pass puts the lamp's falloff back over the glass. So
the device is real, and the screen on it is whatever the scene says.

The screens (`screens/`) follow the firmware's own layout — specifically
**CanvasTheme** (`src/components/themes/canvas/CanvasTheme.h`), which is the
theme that actually ships: `UITheme::setTheme()` constructs one unconditionally
and no setting swaps it. BaseTheme's Classic metrics are an inherited default
that nothing selects, so laying these screens out against Classic drew a device
that does not exist.

What that means on screen: a 44 px header with the title **left**, a 1 px rule
under it and a bar-style battery with its percentage in the title font; 44 px
rows whose selection is a 2 px **underline**, not an inverted bar — the theme
exists to avoid repainting a filled row; and a flat grey hint bar with
quarter-width slots rather than four outlined boxes. The chrome is set in
**Ubuntu** (`UI_10` / `UI_12` in `src/main.cpp:121`), not Noto — Noto is the
book. The reader's status row is battery + percent, the chapter centred, then
`page/pages  percent`, over a full-width progress bar.

Two screens draw themselves rather than going through the theme, and the mocks
follow them: `AskBookActivity::renderKindMenu` (so the Ask menu's selection
really is an inverted inset bar) and `DictionaryDefinitionActivity`, which shows
both a dictionary entry and the agent's question — which is why those two screens
are identical.

## What it says

Open → the agent is in the firmware, as a row in the reader's own menu (the
passage is chosen by `choosePassageWindow()`, not selected by hand) → what the reader measures
from page turns (regressions, pace vs the reader's own baseline —
`EpubReaderActivity.h:126`, `InkAgentProtocol.h:57`) → the reading features
(Focus Reading, offline StarDict dictionary, typography and SD fonts, tilt page
turn on the X3, KOReader/Calibre/OPDS, reader-to-reader transfer) → what it
keeps (Words, Highlights, Read later, Reading canvas) → the app drawer and its
ceiling → close.

## Sound

Both tracks are generated by `audio/`, so the film has no third-party asset in
it and nothing to licence.

`audio/score.py` writes the soundtrack against this edit rather than to fit it.
It runs at 120 bpm, which is the cut's own grid (`theme.ts`: `BEAT = 15` frames
at 30 fps), so the plucks land on the cuts; aeolian on D, one chord per scene
with the changes on the scene boundaries, and the only major triad is the lift
under Apps. A filtered noise swell rises into each cut — the picture's
transition is a panel refresh, so the sound arrives and stops rather than rings.

`audio/vo.py` speaks `audio/script.json` through macOS `say`, one clip per line,
laid onto the bed at the timestamp each line is cued to. It levels every line to
the same RMS and **prints an OVERRUN for any line that runs into the next cue**
— a line that does not fit its shot is a script problem, and the script is
written to the frame counts in `Root.tsx`. The music ducks 8 dB off the
voiceover's own speech envelope, not a sidechain guess.

`audio/master.sh` runs after the render: two-pass EBU R128 to −16 LUFS with
1.5 dB of true-peak headroom, video stream copied. `npm run render` does both.

**The voiceover is a placeholder.** It is macOS `say` (Daniel, en_GB) — the
timing, the script and the mix are finished, the performance is not. Recording a
human against `audio/script.json` and dropping the file in as `public/vo.wav`
needs no other change.
